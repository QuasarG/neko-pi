## 1. 先读这一页

目标是让长期使用带来更准确的用户理解和可复用的项目经验，同时避免记忆膨胀、项目内容串入人设、重复注入背景以及后台任务覆盖新事实。

| 决策 | 具体含义 | 目的 |
| --- | --- | --- |
| 六种记忆类型保留 | `promise`、`episode`、`anchor`、`whisper`、`profile`、`procedure` | 不再把已有类型强行合并成四类 |
| 增加项目作用域 | 每个真实工作目录有独立身份、工作记忆和历史索引 | 同名目录、不同工作树和不同项目不混用经验 |
| 类型与作用域分开 | 一条记忆同时有 `type` 和 `scope`；项目工作记忆不是第七种类型 | 共用更新通道，隔离读取和保存目的地 |
| Markdown 保存正文 | 规范文件名，保留普通文件可读写性 | 沿用已有工具，不创建专用 read 工具 |
| SQLite 保存元数据及运行状态 | 目录、版本、活动、连续状态、衣橱、消息快照和同步进度 | 多会话、跨进程有统一的变化判断依据 |
| 按需读取 | 模型通过目录知道文件用途，自行决定读哪些内容、是否整读 | 不每轮自动关键词召回，不强制读一个大模块或全库 |
| 稳定的消息历史 | 新消息的时间和变化快照固定保存；旧消息不重算 | 支持恢复、重试和相同前缀复用 |
| 严格区分可用与已知 | 文件变更、上下文已保存、工具结果已交付分别记录 | 不漏掉后台变化，也不反复通知已知结果 |
| 谨慎保存工作记忆 | 只保存有长期价值、可复用的事实和经验 | 工作记录不退化为命令日志或逐轮流水账 |
| 人设记忆允许更宽松 | 保留有意义的偏好、关系背景、个人经历与 `whisper`；定期整合 | 保持个性，同时合并旧条目和重复内容 |

明确不做：RAG、Embedding、向量库、每轮额外总结请求、人设自动评分重写、远程控制、多媒体生成、强制全库阅读、未经确认的人设核心改写。

## 3. 不可破坏的边界

1. 产品运行数据只在 `~/.neko_pi`，或用户显式配置的 `NEKO_PI_HOME` 下管理。
2. 不扫描、导入、修改或迁移 `.neko_mem`。它服务于其他 agent。
3. 不修改外部 `AGENTS.md`。既有人设母本不参与这轮迁移。
4. 人设内容留在私有安装目录；公共源码和文档不包含具体私人人设、私密记忆或生成图片。
5. 使用既有文件阅读工具。读取部分还是全文由模型根据任务需要决定。
6. 不要求每次维护都读全库、重建摘要，或自动启动一次额外模型调用。
7. 人设核心不会因记忆维护自动改变；普通记忆内容不能变成高优先级指令。
8. 工作产物保持专业；StyleBank 只能影响聊天表达。
9. 数据迁移不得静默丢弃、改写意义或重新归属旧记录。
10. 本规范批准前，不修复检查点中的功能缺陷，不建立真实 SQLite 数据库，不搬动实际文件。

## 4. 类型、作用域与值得保存的信息

### 4.1 六种类型保持语义

| 类型 | 保存什么 | 人设作用域示例 | 项目作用域示例 |
| --- | --- | --- | --- |
| `profile` | 稳定的对象资料、偏好 | 沟通方式和长期偏好 | 项目固定环境、约定与限制 |
| `anchor` | 值得长期保留的重要事实 | 经确认的重要背景 | 架构决定及其关键原因 |
| `promise` | 有状态的约定 | 有效约定及兑现状态 | 已确认的长期跟进事项 |
| `episode` | 有意义的经历 | 对后续理解有用的共同经历 | 有复用价值的故障、发布或决策经过 |
| `procedure` | 可复用的处理方式 | 有依据的协作方法 | 可复现的排查、验证、部署经验 |
| `whisper` | 私人想法、期待或未形成约定的愿望 | 保留主观性质及时间，不伪装成用户已承诺的事实 | 类型仍被保留，但不能借此放入个人关系内容；项目中的设想须标明未经确认 |

类型不决定重要程度，旧记录也不天然失效。重要性、有效状态、实际发生时间、更新时间分别表达。

### 4.2 两个独立作用域

- `persona`：全局人设相关记忆，由不同项目会话共享。
- `project`：必须携带 `project_id`，只在相应工作目录会话中自动可见。
- 每条记录只归属一个作用域。不得创建一条同时属于人设和项目的记录。
- 同名主题在两个作用域内允许存在，具有不同记录 ID，不做跨作用域去重或覆盖。
- 需要转移归属时，必须有明确的用户操作，并保留来源；不得由自动维护推断迁移。
- 同一轮同时出现个人偏好和项目经验时，拆成两个独立写入请求。
- 同一流水线负责校验、版本检查、保存、元数据更新和活动登记，输入的作用域决定目的地及可见范围。

### 4.3 模型应遵循的维护要求

| 情况 | 处理 |
| --- | --- |
| 用户明确要求记住 | 最高优先级处理，明确告知成功或失败，不能静默忽略 |
| 已确认的长期偏好、纠正或重要背景 | 更新同主题记录，保留新旧事实的时间和状态关系 |
| 承诺建立、兑现、取消或调整 | 更新原事项状态，避免继续作为待办出现 |
| 项目中形成可复用结论 | 记录问题、关键依据、结论和复用条件，不复制整段工具输出 |
| 普通工具输出、一次临时任务或常规收尾 | 不自动保存工作记忆 |
| 有意义但较主观的人设经历或 `whisper` | 可以保存，标明主观性质；定期整合，不要求每轮都产生一条 |
| 短暂场景和情绪 | 优先近期连续状态，不自动固化成用户永久属性 |
| 不确定或互相矛盾的信息 | 标明不确定性，不擅自合成确定事实 |

回复结束前应判断是否有值得维护的信息，但不为完成检查而强行写入一条记录。

## 5. 项目身份：目录字符串与哈希同时保留

目的：同名目录不会撞名，符号链接的同一目录不会无意形成两份项目，同一仓库下不同工作目录不擅自共享工作记忆。

建议算法，待本规范批准：

1. 取会话实际工作目录，不取进程偶然所在的 vendored TUI 目录，不自动提升到 Git 根目录。
2. 解析为绝对路径；目录存在时取 `realpath`，保留用户原始路径作为显示与排错字段。
3. 统一路径分隔符；保留平台有效的大小写语义，不自行全部转小写。
4. 对规范路径的 UTF-8 字节计算完整 SHA-256，作为 `project_id`。
5. 文件夹命名为 `<可读目录名>--<哈希前16位>`。完整规范路径和完整哈希存入 SQLite；若短哈希发生冲突，扩展哈希长度。

例：`service--e9…` 只是可读目录名加哈希的示意，不是真实项目 ID。

| 情况 | 归属 |
| --- | --- |
| 两个路径 basename 相同，完整目录不同 | 不同项目 |
| 符号链接指向同一个真实目录 | 默认同一个项目；显示路径可不同 |
| Git worktree 位于另一个目录 | 不同项目，不自动合并 |
| 父目录和子目录分别作为 cwd | 不同项目，符合“工作目录”口径 |
| 项目移动或重命名 | 默认新项目；提供显式关联／迁移方案，不能靠 basename 猜测 |
| 旧 cwd 已不存在 | 保留既有项目 ID 和历史，不在打开旧会话时重新计算并换身份 |

## 6. 文件布局和命名

目标布局示意；批准前不执行搬动：

```text
~/.neko_pi/
  persona/
    persona.md
    voice/style.md
    stylebank.json
  memory/
    persona/
      <类别>-<明确主题>--<短记录ID>.md
    projects/
      <目录名>--<目录哈希>/
        records/<类别>-<明确主题>--<短记录ID>.md
  runtime/
    state.sqlite
  sessions/
    ...既有原生历史与桥接历史...
  migrations/
    ...迁移清单及可恢复备份...
```

- 正文文件名以“类别＋明确主题”为主体；短 ID 只用于重名和改名后的稳定关联。
- Markdown frontmatter 至少包含：记录 ID、类型、作用域、项目 ID（如有）、主题、状态、实际发生时间（如已知）、创建与修改时间。
- SQLite 索引额外保存：相对文件路径、正文内容哈希、记录版本、作用域版本、大小及整理状态。
- 文件重命名不制造新事实；记录 ID 保持不变。
- 不通过“文件名相同”推断两条记录相同，也不通过标题猜测项目归属。
- 历史正文副本保留在对应作用域的历史存储中，默认不进入模型目录和自动注入。
- 普通原生聊天历史继续保留原格式；SQLite 只记录其会话、消息与项目关联，不因增加项目索引重写历史正文。

## 7. 全局共享状态表

| 对象 | 事实源 | 谁读取及如何到达模型 | 何时更新 | 可见范围 |
| --- | --- | --- | --- | --- |
| 人设核心、语气 | 既有 persona Markdown | Harness 编译稳定系统段落 | 用户配置修改 | 全部会话 |
| 人设记忆正文 | persona scope Markdown | 模型按目录使用现有 read | 同一记忆写入通道 | 全部会话 |
| 项目工作记忆正文 | project scope Markdown | 当前项目目录提示，模型按需 read | 同一记忆写入通道，必须指定项目 | 仅当前项目 |
| 记忆目录及版本 | SQLite | Harness 生成小型目录或变化清单 | 成功写入、人工修改、改名或删除 | 按 scope 过滤 |
| 消息时间、版本与快照 | SQLite＋原生历史关联 | 隐藏运行上下文，和消息固定绑定 | 消息接收并可靠保存时 | 当前会话 |
| 全局活动 | SQLite | Harness 读取新活动；不调用模型总结 | 用户发言、成功维护、换装等明确事件 | 过滤后提供；保留21天 |
| 人设连续状态 | SQLite | 首次或版本变化时的隐藏快照 | 有意义的阶段变化 | 全局；不混入项目进度 |
| 项目工作连续状态 | SQLite，带 project_id | 当前项目会话按需获得 | 项目阶段变化 | 仅当前项目 |
| 衣橱及当前服装 | SQLite | 首次需要背景或换装时提供快照 | 配置修改、首次选择、六小时全局空闲后选择 | 全局 |
| StyleBank 规则 | 既有可编辑 JSON | 工具事件钩子单独提供隐藏表达提示 | 用户编辑规则 | 规则应用于聊天表达 |
| 会话目录及项目关联 | SQLite，引用原生历史 | TUI 会话树、最近列表和标签页 | 创建、命名、状态变化、归档 | UI 可列所有项目；模型上下文不因此跨项目 |

“UI 能列出另一项目”与“另一项目内容进入模型”是不同权限边界。

## 8. SQLite 的职责及逻辑结构

SQLite 不是 RAG，也不存向量。只负责确定的状态、目录、版本、关系和事务。

| 逻辑表 | 关键字段／用途 |
| --- | --- |
| `projects` | 完整项目 ID、规范目录、原始显示目录、可读名称、创建时间 |
| `memory_records` | 稳定记录 ID、六种类型之一、scope、project_id、路径、内容哈希、状态、版本、时间、字节数 |
| `memory_changes` | 单调序号、记录 ID、作用域、修改类型；删除也保留变化墓碑 |
| `scope_versions` | persona 及每个 project 的当前版本，用于消息快照比较 |
| `sessions` | 桥接 ID、原生 ID、项目 ID、标题、历史路径、运行及归档状态 |
| `messages` | 稳定消息 ID、接收时间、原文、模型用运行快照、哈希、消息状态及关联 ID |
| `message_memory_versions` | 本条消息接收时的 persona 版本和当前 project 版本 |
| `context_receipts` | 实际保留在该会话上下文中的背景版本、工具成功事件及交付凭据 |
| `activities` | 序号、时间、来源会话／消息、scope、project_id、事件类型、有限载荷及来源引用 |
| `continuity` | scope、project_id、版本、内容、更新时间和过期时间 |
| `outfits`、`wardrobe_state` | 可配置服装、锁定项、当前选定项、版本、全局最近用户交互时间 |
| `write_journal` | 文件与数据库双写的待完成记录，用于崩溃恢复 |
| `schema_migrations` | 数据库版本及成功迁移记录 |

实现阶段须先确认当前 Node/Bun/发布二进制支持的 SQLite 驱动；不得在文档阶段新增依赖。需要直接 registry 依赖时必须精确固定版本，并按仓库规则审查 lockfile。

数据库写入使用短事务、忙碌超时和有界重试。绝不在等待模型生成、用户回复或网络请求时持有数据库写锁。多进程连接共享同一数据库，不依赖单个进程中的 Map 作为全局事实。

## 9. 各作用域如何确保不交叉

1. 每次维护显式确定作用域；项目写入使用当前会话固定的 `project_id`，不能随全局最后活跃会话改变。
2. 普通目录和变化查询只返回 `persona` 加当前 `project`；其他项目的记录、摘要、正文和查询原文不自动注入。
3. 当前项目的工作结论不能写进人设连续状态；个人体验和关系记忆不能塞进项目文件。
4. 底层统一活动表可以记录所有项目，但 prompt 查询必须进行作用域过滤。全局最近用户交互只用时间计算换装，不携带其他项目正文。
5. `user_query` 的正文默认属于来源项目的活动，不自动当作人设记忆，也不复制到其他项目。
6. 用户明确要求访问另一个项目时，走显式的作用域选择；不建立默认跨项目联想或自动传播。
7. 同一 scope 内不同会话可以共享经验与历史关联。项目完整聊天历史仍以原生会话为单位，不整段注入其他会话。
8. 原有全局记忆归属不明的技术条目在迁移时列为待人工确认，不按当前 cwd 自动全部归入某个项目。

## 10. 接收、排队、交付与缓存稳定性

### 10.1 消息接收

桥接层收到合法新消息后，在可靠保存前完成以下确定性操作：

1. 分配稳定消息 ID，校验重复请求，固定接收时间和时区。
2. 固定来源会话、project_id、活动截止序号、persona 版本和当前 project 版本。
3. 查出当前会话尚未知晓且当前作用域允许看到的变化。
4. 确定是否需要当前服装、连续状态或记忆目录快照；相同且仍在上下文中的版本不重复附加。
5. 将原文、模型用运行快照、版本和排队状态可靠保存，再确认接收成功。

排队十分钟后开始执行，仍然使用这条消息的接收时间和已冻结快照。执行期间产生的新变化留给之后的同步，不回写这条旧消息。

### 10.2 已接收不等于已交付

- 保留“最近已接收消息的元数据版本”，用于表示用户要求的发送时状态。
- 另保留“可靠存在于会话请求历史中的通知／背景”，用于判断是否还需补交。
- 取消待执行消息时，消息携带但尚未交付的通知不得永久算作已知。
- 如果后续消息已经冻结，恢复遗漏应生成新的、一次性的补偿上下文，不修改已有消息快照。
- 若工具成功结果已经进入会话历史，记录该具体事件已知；不能把总游标直接跨到该事件序号，跳过期间其他会话的未知事件。
- 模型服务失败后的重试复用同一消息及快照，不新增一次活动。若消息根本未进入原生历史，应保持可重投状态。

### 10.3 不重复背景

普通连续 query 仅必带新时间。没有新活动时省略活动块，不写“无变化”。人设未变不更新系统段落；衣服、目录、连续状态未变且仍在模型历史中时，不再复制。

模型输入中的活动和记忆均标记为数据，不将其他会话的 query 当作当前指令。SQLite 和侧栏里存在某个状态，不代表模型自动知道它。

### 10.4 长度与缓存

- 活动注入有独立字节预算，超出时给出省略数量和可读取的来源引用；不能一边省略关键变化一边声称已经全量交付。
- 若活动已超过21天，明确提示可用范围有限；记忆目录仍以当前版本核对，不能把活动过期等同于事实未更新。
- 21天清理只作用于活动库。已写入旧会话的时间、活动和服装快照保持不变。
- 会话压缩是显式上下文变化。压缩后若关键背景不再保留，即使版本没变也可重新提供当前快照。
- 缓存验收比较最终 provider 请求，而不只比较本地对象。人设更新、工具 loadout、模型或接口切换和压缩单独归因。
- 只能宣称前缀稳定性得到验证。实际厂商命中率、有效期和计费需要实际接口数据，不能由离线测试保证。

## 11. 一轮 agent loop

```text
接收并持久化用户原文、时间、版本和必要变化快照
  -> 排队／分发到固定会话和固定项目
  -> 构造：稳定人设 + 本会话历史 + 新消息运行上下文
  -> 模型根据目录与现有依据判断是否需要阅读文件
  -> 如需要，现有 read 返回所选范围，不强制整模块或全库
  -> 正常执行任务工具
  -> 仅在有价值时通过统一通道维护相应 scope 的记忆
  -> 工具成功后登记版本与事件；StyleBank 如命中则提供聊天提示
  -> 模型完成回复
```

没有有价值的新记忆时，直接结束。活动、目录比较和换装均不启动独立模型请求。按需读文件和维护工具仍然可能产生正常 agent loop 的额外往返，必须如实计入成本。

## 12. 统一维护通道与并发

### 12.1 统一流程

`scope 选择 -> 内容及类型校验 -> 稳定 ID/主题查找 -> 读取版本核对 -> 保存正文 -> 登记元数据版本 -> 记录变化 -> 返回真实结果`。

沿用既有 `memory_write`，扩展必要的 scope 参数；现有普通 write/edit 若修改受管记忆，也进入相同校验与索引流程。不得再增加一套互不相干的人设／工作写入实现。普通文件读取工具不换 API。

### 12.2 晚完成任务的四种情况

| 场景 | 正确结果 |
| --- | --- |
| 用户先发给 A，再发给 B；A 后完成 | A 的有效新记录仍可保存，不能仅因 B 后来活跃就丢弃 |
| A、B 修改不同记录 | 两项都保存，无需互相拒绝 |
| A 读取旧记录，B 更新该同一记录，A 后写 | A 不能覆盖新版本，返回冲突并要求重新核对 |
| A 写入成功但尚未向其历史交付结果 | 保留事件待交付，不根据来源会话 ID 跳过通知 |

每条记录的乐观版本检查负责事实一致性；不能拿“最新活跃会话”代替所有记忆写入的权限。

### 12.3 文件和数据库双写

Markdown rename 与 SQLite commit 不是一个原子操作，必须正面处理：

1. 受管写入记录稳定 operation ID、旧哈希、新哈希及待写内容引用。
2. 短暂串行化同一记录的版本检查与落盘；先持久化恢复日志，再原子替换正文，最后提交索引／事件。
3. 启动恢复根据日志与实际哈希完成缺失登记或明确报告冲突。
4. 重试同一 operation 不重复增加版本和成功事件。
5. 人工绕过 Harness 修改文件时，目录核对发现内容哈希变化，登记为外部修改；不能假设外部编辑器遵守数据库锁。
6. 无法确定哪份正确时保留双方可恢复内容，报告需要处理，不静默选择较新 mtime 覆盖。

## 13. 记忆增长与定期整合

项目记忆必须有可复用价值；人设记忆较宽松，尤其 `whisper` 允许有意义的主观内容，但不能成为无限逐轮日记。

整合触发：同主题重复、达到有效集合预算、存在许多已完成／失效内容，或距离上次整合达到周期且确实有新记录。周期只是检查机会，不要求每隔固定天数无条件调用模型。

| 操作 | 要求 |
| --- | --- |
| 合并旧记录 | 保留有用事实和时间，不将多次经历改写成一次 |
| 处理 whisper | 合并相近的旧想法，保留主观状态；不能改写成用户答应过的约定 |
| 整理承诺 | 兑现／取消更新状态，未完成旧约定不能因“太旧”而消失 |
| 整理项目经历 | 提炼复用条件，保留失败原因和必要限制，不只留下“问题已解决” |
| 容量到限 | 先整理，不能通过新建更多小文件绕过限额 |
| 整合失败 | 旧正文仍有效，不删除原记录，不伪造成功状态 |

待审定的起始预算建议，而非本次已确认数值：persona 有效正文64 KiB；每项目有效正文32 KiB；单条正文16 KiB；单次自动活动注入8 KiB。字节预算不是精确 token 预算。

历史副本与数据库也必须有空间统计和上限。建议起始历史预算 persona 256 MiB、每项目64 MiB，达到后暂停自动新增并提示整理／导出，不未经确认永久删除旧事实。明确要求保存但因硬上限失败时，必须告知尚未保存，不能返回成功。不能同时承诺永久保存所有版本和磁盘绝不增长。

此阶段不强制统一模型摘要。目录用途说明与确定的版本变化足以导航；可选摘要只在明确请求或将来批准的整合动作中生成，且仍按 scope 隔离、标注来源版本，不能替代事实文件。

## 14. 衣橱与 StyleBank

衣橱全局共享：首次选择；六小时以上没有任何用户新消息，下一次接收消息时重新选择；尽量不重复上一套；锁定优先；配置为空则跳过。后台任务、活动通知和单纯切标签不刷新用户活跃时间。

SQLite 保存服装定义、当前项及版本；从现有 `wardrobe.json` 导入时保留所有启用状态和锁定项。配置修改不重算旧消息的外观。

StyleBank 第一版只搭通用框架：按真实工具名、受支持命令匹配、成功／失败和冷却条件选择少量提示。提示单独作为隐藏上下文，原始工具内容、代码、文档和提交信息不被污染。规则为空则无注入，不内置具体人设表达。

复杂 shell、引号、管道或组合命令在没有可靠解析器前不匹配，必须在文档和测试中说明限制，不能宣称支持任意命令。

## 15. TUI 与后端联动

右侧独立会话卡片采用“按项目的会话树＋最近”，点击后通过既有顶部标签页打开并加载。已有标签切到对应项，不重复打开同一会话。

- 项目分组使用真实 project_id／目录，不能只用所有项目相同的 `pi` 标识。
- 会话与项目映射固定保存，切换标签不能改变正在运行任务的 cwd 和记忆作用域。
- 状态／立绘区域保持空白，不放占位图、服装预览或替代文案；`/neko` 仍可按需查询状态。
- 宽窗口显示卡片；窄窗口使用 `/sessions` 和现有键盘操作。
- 支持新建、打开、搜索、重命名、状态显示、恢复、归档和取消等实际实现的能力。
- 检查继承前端的所有可见入口。后端不支持的入口应明确不可用或隐藏，不能靠返回空数组伪装实现。
- 多进程显示同一会话时，至多一个后端拥有该原生会话的写入执行权；另一个不能同时恢复并继续写同一历史。
- 新会话不因后台准备就调用模型；只是看标签也不创建活动通知。

## 16. 迁移与恢复

### 16.1 只处理产品自己的运行目录

本次迁移只处理 `~/.neko_pi` 内的既有记录、JSON 状态和会话映射，不再导入其他 agent 的路径。源码检查点／tag 不包含私有运行目录，不能把 Git tag 当作私人数据备份。

### 16.2 迁移步骤

1. 盘点内部数据，生成 dry-run：文件数、类型、大小、哈希、旧会话映射、归属不明确项、失败项。
2. 在内部迁移目录形成受限权限备份与清单，验证可恢复，再开始写入。
3. 建立带 schema version 的 SQLite；导入 JSON 活动、连续状态、衣橱和会话元数据。
4. 为旧记忆分配稳定 ID，保留六种类型和所有语义字段。已知人设记录进入 persona；项目归属不明的技术记录保留待确认，不猜测。
5. 文件命名调整保留 old_path -> new_path 映射；不重写旧聊天／工具结果中已经存在的路径文本。
6. 为旧会话建立基线。首次新消息提供当前必要目录与迁移说明，随后按版本同步；不伪造过去已有的通知记录。
7. 验证记录数、内容哈希、状态、时间和历史引用，再切换主读写路径。
8. 迁移可重入，重复启动不会重复导入事件／记录。失败保留原件，提供明确恢复结果。

### 16.3 回退

未接受新写入前可回到备份；接受新写入后不能简单覆盖为旧数据库。必须先导出迁移后的新记录和变更，再进行受控恢复，避免回退导致新事实丢失。旧程序不得和迁移后的程序同时写同一记忆库。

## 17. 验收及批准门槛

配套 todo 给出逐项测试矩阵。每条必须有明确结果或证据，不以“跑过一遍前端”替代。

- 后端自动测试使用 harness＋faux provider，不访问真实付费模型。
- 数据库并发和崩溃恢复用临时运行目录，覆盖两个进程、不同记录、同一记录及写入各阶段中断。
- TUI 用真实 native renderer、真实 bridge 和受控后端，验证点击、标签、历史加载、队列、模型选择和错误状态。
- 最终 provider 序列化请求做稳定前缀对比；真实厂商缓存指标单独记录为尚未验证，除非获得实际接口证据。
- 不以删除功能、放宽事实断言或改变测试期望来掩盖缺陷。旧断言因批准后的需求变化而更新时，必须加上新行为对应断言。

审定重点：项目 cwd 身份策略、scope 隔离、SQLite／Markdown 分工、按需阅读、增长预算及清理方式、排队取消补通知行为。用户批准后，再按 todo 的顺序实现；如实现发现必须改变这些行为，先更新设计并说明。
